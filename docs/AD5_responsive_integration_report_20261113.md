## 1. 결과와 판단 기준

**기존 화면 배치와 카드 안무를 재사용하고, 확인된 계산 불일치만 수정했다.** 카드·설명창의 배치 구조를 새로 구성하지 않았다. 반응형 동작을 모두 하나의 확대 배율로 바꾸지도 않았다.

세로 버튼 가로 비율, 열린 메뉴 항목의 끝선·안내 화살표, 짧은 PC 창의 공간 부족, 진행 중 회전 시 애니메이션 좌표·크기 갱신을 수정했다. 카드 이미지·오디오 등 106개 자산은 모두 원본과 바이트가 같다.

이번 전달물에서 별도 360×800 참고 이미지 파일은 확인되지 않았다. 따라서 **첨부 ZIP을 360×800에서 직접 실행한 화면**을 보존 기준으로 삼았다. 이 화면의 카드·버튼 크기는 수정 전후 같았다. 별도 이미지와의 시각 일치 여부는 미확인이다.

## 2. 기존 구조에서 정상 작동하며 유지한 부분

- `viewportSpace()`의 실제 너비·높이와 단계별 `stageSize()` 크기 진입점.
- 세로의 4vw/4dvh 바깥 여백, 제목·카드·설명·버튼의 기존 순서.
- 세로 글자·버튼 높이의 기존 높이 축, 설명 영역의 너비·내부 스크롤.
- 스마트폰·폴더블 가로의 중앙 카드 무대와 오른쪽 아래 버튼, 공개 후 카드 왼쪽·설명 오른쪽 구성.
- 넓은 터치 가로의 중앙 무대·고정 중앙 버튼과 2열 결과 화면.
- PC의 기본 중앙 무대, 일반 결과 2열 및 넓은 PC 결과의 3행 grid.
- 카드 프레임 높이/너비 `2128/1240`, 앞면 이미지 `object-fit:contain`.
- 22장 셔플·20장 선택 풀·7장 가시 팬, 드래그·선택·두 번째 입력 공개.
- 기존 안무의 회전 각도·타이밍·3D 깊이·이동 곡선. 화면 변경이 없는 대표 6조건에서 원본/수정본 프레임과 시간이 일치했다.
- 첫 화면의 금빛 마스크, 카드 강조·별똥별·배경·음악 코드와 원본 자산.
- 이미 들어 있던 `Carousel.cachedGeometryKey`의 너비·높이·프로필 캐시와 공개 완료 후 크기 보정. 이전 AD4 보고서의 오류를 그대로 현재 오류라고 판단하지 않았다.

## 3. 확인된 문제 → 원인 → 수정

### R01. 넓은 세로 화면에서 버튼만 과도하게 넓어짐 — 실제 화면·수치 확인

**위치:** 원본 `js/settings/config/config.js:138`, `css/screen/23-portrait-responsive-scale.css:10`. 수정본 config `:156`, CSS `:10`.

카드는 `min(W/390,H/844)`로 제한되지만, 버튼 너비는 `W/390`만 사용했다. 673×841에서 카드 너비는 약 145px인데 버튼 묶음은 488.34px이었다. 이는 서로 다른 계산을 쓴다는 사실만이 아니라, 기준 화면과의 가로 비율이 실제로 달라진 경우다.

**수정:** 기존 `scale`을 `portraitControlX`로 전달하고 셔플 버튼·드롭업·간격·관련 가로 내부 여백에만 연결했다. 제목·설명창·바깥 여백의 위치와 기존 세로 축 글자/높이는 유지했다.

| 화면 | 팬 카드 너비 전→후 | 버튼 묶음 전→후 | 전체 투영 팬 대비 버튼 폭 전→후 |
|---|---:|---:|---:|
| 360×800 | 135→135px | 261.20→261.20px | 40.45→40.45% |
| 673×841 | 145→145px | 488.34→281.98px | 70.06→40.46% |
| 1024×1366 | 236→236px | 743.05→458.02px | 65.63→40.46% |

카드 너비는 DOM 반올림값이다. 전체 팬 폭은 회전된 카드 사각형 전체의 좌우 범위이며 화면 밖에 있는 부분도 포함한다. 기존 휴대폰 세로 팬의 양끝 부분 노출을 유지했다. 카드·버튼의 중심은 계속 화면 중앙이다.

**영향:** 세로의 선택 화면과 결과 버튼. 높이가 충분한 360×800에서는 기존 수치를 유지한다. 화면 공간이 다른 경우 너비만 늘어나던 불균형이 줄어든다.

### R02. 메뉴 패널은 정렬되지만 항목의 끝선은 안쪽에 있음 — 실제 측정

**위치:** `css/screen/01-foundation-and-cards.css` 원본 `:523`, 수정 `:524`, `:552`.

원본의 열린 메뉴 패널은 메인 버튼과 폭이 같았다. 내부 패널 padding 때문에 항목의 좌우 끝은 360×800에서 각각 약 3.69px, 1024×1366에서는 약 10.50px 안쪽이었다.

**수정:** 패널의 가로 padding을 0으로 하고, 그 값을 항목의 텍스트 padding에 더했다. 항목의 클릭·강조 영역은 메인 버튼 끝선에 맞고 글자의 기존 안쪽 여백은 보존된다. 배경·테두리 0·둥근 모서리·글자 크기·세로 여백·160ms 열림 효과는 유지했다.

18조건의 항목 좌우 오차는 측정상 0px이었다. 기존 문서 중 88% 메뉴 폭을 설명하는 내용은 과거 기록이며, 현재 ZIP의 실제 100% 패널 폭을 기준으로 수정했다.

### R03. 열린 메뉴의 안내 화살표가 글자 위를 가림 — 실제 캡처·사각형 확인

**위치:** `css/motion/04-fan-layout.css:66`, `js/screen/app/events.js:32`.

JS는 메뉴 높이를 측정해 `--ad2-menu-open-height`를 쓰지만, CSS에서 메뉴 위로 화살표를 올리는 규칙이 터치 가로 class에만 제한되어 있었다. 세로와 PC에서는 열린 항목과 화살표 사각형이 겹쳤다.

**수정:** 기존 `is-menu-open` 규칙을 모든 배치에 적용하고, 메뉴 오프셋과 화살표의 최대 하강 폭을 같은 식에 포함했다. 화살표 그림·크기·왕복 시간·이동 폭은 바꾸지 않았다.

```text
열린 메뉴의 화살표 bottom = 버튼 높이(100%) + 메뉴 offset + 메뉴 실제 높이
                         + 11px × 기존 arrowScale + 6px
```

정지 위치만 보고 고정 14px을 더하면 큰 세로 화면에서 내려오는 화살표가 다시 메뉴에 닿는다. 최종 식은 최대 하강 시점에도 6px을 예약한다.

| 실제 브라우저 조건 | 최대 하강 위치의 메뉴와 간격 |
|---|---:|
| 360×800 세로 | 6.01px |
| 673×841 세로 | 6.01px |
| 1024×1366 세로 | 5.99px |
| 680×500 PC | 6.00px |
| 800×360 터치 가로 | 6.00px |
| 1180×820 터치 가로 | 6.00px |

QA에서 CSS 왕복 애니메이션을 480ms(최대 하강 keyframe)에 잠시 고정해 실제 사각형을 측정한 뒤 재생을 재개했다. 이 QA 제어는 시험본 ZIP에 포함하지 않았다. 자연 재생의 1.2초 관측은 환경상 2~3회 샘플이라 실기기 프레임률 증거로 쓰지 않았다. 전체 이동 범위의 간격은 기존 0~11px 이동 범위와 위 최대 위치 검사로 확인했다.

### R04. 짧은 PC 창에서 최소 무대가 실제 높이보다 큼 — 실제 재현

**위치:** `css/screen/01-foundation-and-cards.css:5`, 원본 `:48`; `css/effects/13-idle-deck-size.css:5`; 수정 config `:93`.

680×500에서 무대 최소 높이 430px에 제목·버튼·여백이 추가되어 버튼 하단이 약 616.4px까지 내려갔다. 버튼으로 접근하면 문서가 스크롤되어 제목이 위로 밀렸다. 단순히 카드가 무대 밖에 그려진 현상과 구분했다.

**수정:** 기존 flex 무대가 실제 남은 높이를 쓰도록 app의 높이를 100dvh로 정하고 경쟁하는 무대 최소 높이를 0으로 정리했다. 첫 덱 CSS도 실제 `--card-w/h`를 읽도록 했다. PC의 원래 카드 크기는 공간이 충분하면 그대로 사용하고, 짧은 무대에서 첫 덱·정지 팬만 제한한다.

팬 하단의 기존 35px drop과 회전된 카드 반높이 투영을 함께 계산한다.

```text
r = 2128/1240
K = (sin(23°) + r*cos(23°))/2
PC selection width = min(기존 210px, max(40px, (stageHeight/2 - 35px - 8px)/K))
PC idle width = min(기존 첫 덱 너비, max(40px, (stageHeight - 30px)/r))
```

680×500의 무대는 약 271.22px, 버튼 하단은 약 457.61px이 되어 첫 화면에서 접근 가능했다. 팬 카드 너비는 210→약 94px로 제한됐다. 1440×900의 기본 팬 210px·결과 260px은 유지했다. PC 글자·버튼 크기·배치 순서는 바꾸지 않았다.

의도된 첫 셔플의 프레임아웃을 제거하는 수정은 하지 않았다. 매우 작은 창에서 모든 글자와 버튼이 차지하는 높이보다 화면이 더 낮은 조건까지 보장한 것은 아니다.

### R05. 진행 중 회전에 현재 경로·크기가 늦게 반영됨 — 실제 타이밍을 지정해 재현

**위치:** 원본 `js/motion/animation/card-animation.js:77`, `:187`, `js/screen/app/events.js:88`. 수정 `card-animation.js:7`, `:86`, `:221`; `center-motion.js:4`; `events.js:93`.

원본은 셔플·중간 펼침의 너비·높이·카드 크기와 프레임을 진입 시 한 번 만들고, resize 처리에서 진행 중 상태를 제외했다.

- 820×1180의 중간 펼침 도중 1180×820으로 회전: 원본은 204px 카드가 남았고 새 계산은 181.41px이었다. 수정본은 181px로 갱신됐다. 관찰한 WAAPI 시간은 회전 후에도 약 1199.8ms였다.
- 800×360 공개 이동 중 360×800으로 회전: 원본은 이동 중 142px, 새 계산은 175.38px이었다. 수정본은 이동 중에도 175px였다.
- **원본도 공개가 끝나면 175px로 보정됐다.** 이 ZIP에 결과 크기가 끝까지 고착된다고 보고하지 않았다. 문제는 진행 중 갱신 지연이다.
- 첫 셔플의 101개 프레임에서도 회전 후 경로의 x/y/z가 새 공간에 맞게 바뀌는 것을 수집했다.

**수정:** 기존 안무를 계산하는 frame builder를 유지하고, 크기가 바뀌면 같은 WAAPI 효과의 keyframes만 다시 지정한다. 중간 펼침의 시계·카드 수·동작 시간을 유지한다. 공개 이동은 현재 화면 위치·각도·배율을 읽어 새 host에 연결하고 내부 뒤집기 애니메이션은 건드리지 않는다.

### R06. 분산된 resize 처리·효과 없는 임시 복제 계산 — 참조 확인

**위치:** 원본 `main.js:52`, `events.js:88`, 원본 events `:106`; 수정 events `:90`, main `:52`, stage-boundary `:36`.

main의 예약 갱신과 events의 즉시 갱신이 같은 UI 변수를 따로 썼다. result resize에서는 숨긴 DOM 복제본으로 버튼 위치를 다시 계산했지만, 결과 변수의 주 사용처는 로딩되지 않는 22번 CSS였다.

**수정:** events의 requestAnimationFrame 예약 처리 한 곳에서 프로필 → UI 변수 → 실제 경계 → 현재 상태의 카드/경로 순으로 갱신한다. stage·버튼·제목의 ResizeObserver, 글꼴 준비, window/visualViewport 변경과 입력 프로필 변경을 연결했다. 필요 없는 result 복제 계산을 제거했다. 선택 중 snap도 현재 offset으로 재배치하며 사용자가 고른 카드를 유지한다.

공개 완료 시 전역 가짜 resize 이벤트를 보내는 대신 같은 예약 함수를 호출한다. 기존 canvas·음악 모듈의 실제 resize 이벤트 처리는 유지했다.

### R07. 같은 팬 크기를 카드마다 다시 계산함 — 활성 호출 관계 확인

**위치:** `js/motion/core/cinema-core.js:36`, `js/motion/selection/carousel.js:87`.

`Carousel`에 단계 크기 캐시가 있는데도 각 `slotPose()`에서 화면·무대 크기를 다시 읽었다. `slotPose`가 선택적으로 이미 계산한 크기를 받도록 하고 carousel·펼침에서 같은 값을 전달했다. 기본 호출 형식도 유지해 다른 호출부와 호환된다.

이 변경의 목적은 같은 프레임의 크기 일치와 반복 읽기 감소다. 실기기 FPS 개선을 측정한 결과는 아니다.

### R08. 태블릿 가로의 설명 아래 공간이 고정 44px을 예약함 — 실제 계산 불일치

**위치:** `css/screen/25-landscape-adaptive-layout.css:175`.

실제 버튼은 `--land-button-h`에 따라 달라지지만 설명 그룹 padding은 44px이었다. 예를 들어 1024×768의 실제 버튼 높이는 약 36.73px였다.

**수정:** 기존 식의 44px만 같은 버튼 높이 변수로 연결했다. 고정 중앙 앵커·본문 글자·두 열 위치·외곽 여백은 그대로다. 이 원인만으로 원본에서 실제 겹침이 발생했다고 단정하지 않는다. 확인된 내용은 예약 높이와 실제 높이의 불일치다.

경로와 행은 새 시험본 내부 기준이며, 기존 파일명과 폴더 구조를 유지했다.
